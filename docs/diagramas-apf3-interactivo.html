Sección 4.5 del Informe APF3

Flujo de Atención de Solicitudes (Registro → Clasificación → Asignación → Atención → Verificación → Cierre)

Proceso estructurado del módulo de Gestión de Solicitudes e Incidencias conectado a PostgreSQL.

1. REGISTRO DE LA SOLICITUD
El usuario ingresa a Solicitudes / Mesa de Ayuda (/app/solicitudes) y selecciona una opción predefinida de su rol en catalogo_incidencia (o redacta un caso especial en "Otros" con captura).
↓
2. CLASIFICACIÓN Y CÁLCULO AUTOMÁTICO DE PRIORIDAD
El sistema clasifica el tipo de solicitud (Información, Acceso, Asistencia o Incidencia) y multiplica Impacto (1..3) × Probabilidad (1..3):
↓
CRÍTICO (9 pts) Atención inmediata
ALTO (6 pts) Prioridad en el turno
MEDIO (3–4 pts) Dentro de la jornada
BAJO (1–2 pts) Consulta informativa
↓
3. ASIGNACIÓN AUTOMÁTICA Y PERSISTENCIA EN POSTGRESQL
Se inserta el ticket en mesa_ayuda_ticket con llave primaria id INT autoincremental (IDENTITY), estado PENDIENTE y solicitante_id. Se registra la traza CREACION en mesa_ayuda_bitacora (ticket_id INT [FK]) y se deriva a la bandeja del rol responsable (Recepcionista, Odontólogo, Admin Clínica o Soporte Técnico).
↓
4. ATENCIÓN OPERATIVA Y NAVEGACIÓN DIRECTA
El responsable presiona "Iniciar Atención" (estado pasa a EN_PROCESO y se enlaza responsable_id). Mediante el botón de acceso rápido (Ir a Agenda, Ir a Ficha de Paciente, Sala Virtual, Consultorio) ejecuta la solución en el sistema.
↓
5. VERIFICACIÓN Y REGISTRO DE EVIDENCIA
El responsable comprueba que el cambio fue aplicado correctamente en el módulo clínico o administrativo y redacta el comentario de evidencia de la solución (o el motivo de rechazo si no procede).
↓
6A. CIERRE: ESTADO ATENDIDO
Se registra fecha_resolucion y el trigger trg_calcular_tiempo_transcurrido calcula los minutos/horas exactos en PostgreSQL.
6B. CIERRE: ESTADO CANCELADO
Se guarda el motivo justificado de cancelación en mesa_ayuda_bitacora y la fecha de cierre para consulta del solicitante.

Sección 5.2 del Informe APF3

Flujo de Integración Continua (CI) en GitHub Actions

Pipeline automatizado de verificación ejecutado en cada envío de código (Backend Java 21 y Frontend React 19).

1. Desarrollo del código
Implementación de mejoras en ramas de trabajo (feature/postgresql-modelo-gamboa, feature/login-base-gamboa, feature/sebastian).
↓
2. Commit
Registro local en Git con formato estandarizado: "v1: se realizaron cambios en...".
↓
3. Push al repositorio
Sincronización hacia los repositorios remotos en GitHub (Luife225/Backend_Dentista y Luife225/Frontend_Dentista).
↓
4. Ejecución del flujo CI (GitHub Actions)
Activación automática del workflow .github/workflows/ci.yml en contenedor Linux limpio (ubuntu-latest) con OpenJDK 21 Temurin y Node.js 22 + pnpm.
↓
5. Compilación o validación
Backend: ./mvnw clean test-compile + verificación de las 24 migraciones SQL Flyway (V1 a V24).
Frontend: Validación estática de tipos con TypeScript (pnpm run typecheck) y vite build.
↓
6. Pruebas automatizadas
Backend: Suite JUnit 5 (HelpdeskServiceUnitTest: 8 pruebas de matriz 3×3, catálogo, bitácora, citas, PDF y teleconsulta).
Frontend: Suite Node Test Runner (13 pruebas de servicios, sesión JWT, inventario y Google Meet).
↓
7. Resultados
Verificación aprobada (BUILD SUCCESS ✅), generación de artefactos de producción (.jar y carpeta dist/) y habilitación para fusión en main y despliegue en Railway Cloud.

Sección 6.2 del Informe APF3

Arquitectura Final Desplegada de Coronyx Dental

Interacción en capas entre el Usuario, Frontend, Backend, Base de Datos e Infraestructura de Alojamiento.

👤 USUARIO FINAL (Navegador Web HTTPS)
Roles autenticados: Paciente, Recepcionista, Odontólogo, Administrador de Clínica y Soporte Técnico.
↓
💻 FRONTEND WEB (React 19 + TypeScript + Vite 6 + Tailwind CSS)
Interfaz SPA con Login en Modo Claro Clínico, Agenda Interactiva, Historia Clínica, Odontograma Digital FDI, Portal del Paciente, Sala de Videollamada (Google Meet / Jitsi) y Tablero de Mesa de Ayuda.
↓ Peticiones REST JSON + Cabecera Authorization: Bearer <JWT>
⚙️ BACKEND API REST (Spring Boot + Java 21 LTS)
Controladores REST (/api/v1/auth, /patients, /appointments, /clinical-encounters, /inventario, /helpdesk), Seguridad Criptográfica (BCrypt + HMAC-SHA256), Reglas Transaccionales y Motor Flyway (V1 a V24).
↓ Conexión JDBC (HikariCP Pool) + Transacciones ACID
🗄️ BASE DE DATOS RELACIONAL (PostgreSQL 16 / 17)
Esquema normalizado en 3FN: Tablas clínicas (clinica, usuario, rol, paciente, cita, atencion_clinica, version_atencion_clinica, version_odontograma), operativas (inventario_insumo, caja_cargo) y de soporte (catalogo_incidencia, mesa_ayuda_ticket [id INT PK], mesa_ayuda_bitacora [ticket_id INT FK] + Trigger trg_calcular_tiempo_transcurrido).
↓
☁️ INFRAESTRUCTURA DE ALOJAMIENTO (Railway Cloud & Contenedores Docker)
Servicios gestionados en Railway Cloud (Frontend, Backend y PostgreSQL) sincronizados con GitHub + Contenedor Docker Jitsi Meet / Google Meet para Teleodontología y variables de entorno seguras (DB_URL, JWT_SECRET, CORS_ALLOWED_ORIGINS).
